# MindCare backend setup (Phase 1)

## Local setup

The project targets .NET 10. It uses ASP.NET Core Identity with EF Core 9 and Pomelo 9 for MySQL 8.4. The MySqlConnector dependency is pinned to 2.6.2, which includes the fix for GHSA-473q-m89c-ghf8.

Set a complete connection string in .NET User Secrets from the project directory. Replace the sample username with a MySQL account that can create the database and tables:

```sh
cd DotNet_Project
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Server=localhost;Port=3306;Database=mindcare_db;User ID=mindcare_app;Password=YOUR_LOCAL_PASSWORD;"
```

The checked-in settings contain only the local host, port, and database name. User Secrets override that value for development. In production, set `ConnectionStrings__DefaultConnection` in the deployment environment or secret store. Never commit real credentials.

## Migrations

The initial EF migration is `Data/Migrations/InitialMindCareSchema`. With MySQL running and the connection string configured, run:

```sh
dotnet tool install --global dotnet-ef --version 9.0.0
dotnet ef database update
```

To inspect the generated migration without changing the database, use `dotnet ef migrations script`.

## Schema overview

- Identity tables are generated by `IdentityDbContext<ApplicationUser>` and use the standard `AspNet*` table names.
- `ChildProfiles` has a unique `ChildUserId` (one profile per child) and indexed `ParentUserId` (many children per parent). Both account foreign keys use restricted deletion.
- `MoodEntries`, `Assessments`, `JournalEntries`, and `ChatMessages` reference a child profile. Their records also use restricted deletion.
- `AssessmentAnswers` references an assessment, has one row per question number per assessment, and constrains question numbers to the initial 1–10 set.
- `JournalEntries` stores `EntryDate` as a database date and uniquely indexes `(ChildProfileId, EntryDate)` to allow one entry per child per day.
- `AIReports` has a unique assessment FK, giving each assessment at most one report.

## Account behavior

Registration creates only Parent accounts. A signed-in parent creates Child accounts at `/Parent/AddChild`; the server assigns the Child role and derives the parent link from the authenticated identity. `/Parent/*` requires the Parent role; `/Child/*` and `/Assessment/*` require the Child role. Logout is a POST protected by antiforgery validation. After sign-in, parents go to `/Parent/Index` and children to `/Child/Index`.

## Manual acceptance walkthrough

1. Start MySQL 8.4, configure User Secrets, and run `dotnet ef database update`.
2. Run `dotnet run --project DotNet_Project.csproj` and register a parent at `/Account/Register`.
3. On the parent dashboard, choose **Add child account** and create an account with a separate email and password.
4. Log out, sign in as the child at `/Account/Login`, and confirm the child dashboard opens.
5. Log out and sign in as the parent to confirm the parent dashboard opens and only that parent’s child profiles appear.
6. In a private browser session, request `/Parent/Index` and `/Child/Index`; each should redirect to login. Sign in under the opposite role and request the protected route to confirm access is denied.

The database migration was generated but could not be applied in the implementation environment because no MySQL server was listening on localhost. The manual database steps above remain to be completed in an environment with MySQL configured.
